## How do I interpret user needs and implement them into a program? How does creating “user stories” help with this?

I think the best way to interpret user needs is to start with the end goal of what they are asking for. Breaking things down into their simplest form is the best way to turn a suggestion or issue a user has into an actionable item that we, as software developers can turn into code. So if we identify the inputs and outputs a program should have, then we can figure out how to implement them into our programs.

User Stories helps us take a suggestion from a user and present it to our teams in a format that shows what a user wants out of our work. Presented in this way, it helps us as developers get the real sense of what the user intended. Sometimes that can be difficult, especially if the user is not articulate about the exact specifics of what they want. User stories bridges that gap. Breaking down an "I want ..." statement, and turning it into a user story that can be used by a programmer is a real skill that needs to be developed, because very few people who are not programmers are going to naturally explain themselves in a way that matches how a software developer thinks.

## How do I approach developing programs? What Agile processes do I hope to incorporate into my future development work?

Before this class, I naturally used the waterfall method. I would write down what I wanted the program to accomplish, list out the steps and break those down into classes, functions, and methods. Figure out how they would work together, and then build it. But, once I was done, I would try to go back and add things in, and I would find it difficult to add things in. Agile fixes that by making modularity a part of the development process which naturally extends to the way we develop programs. If I am only working on one small section of the program, then I have to build it in a way that forces me to make it more modular. I hope to make this the natural way that I develop programs in the future. I think that forcing myself to work in blocks rather than all at once, will make my programs more maintainable and easier to update and change.

## What does it mean to be a good team member in software development?

A good team member is a good communicator. It shouldn't be expected of us that we will know everything on day one. We shouldn't expect that our knowledge of a given programming language will instantly make us a valuable member of the team. What is expected of us is that we should be ready and willing to ask for help where we need it, and we should be able to explain our strengths, and just as importantly, our weaknesses. In almost every job I've ever had, being a good communicator that brings a positive attitude to the work environment is valued by management much more than having any specific skill. While having certain skills is always important, communication is how you go from a new hire to a real contributing member of the team.
